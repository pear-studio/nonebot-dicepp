# Prune Pear

启用后只调查和汇报，不设计具体接口、不编写迁移方案，也不修改代码或文档。目标不是找出所有可以改动的地方，而是找出当前最值得修复的架构复杂度。

## 调查范围

用户指定范围时聚焦该范围，并按范围大小调整观察尺度；局部问题只要确实值得修复，也可以指出。用户未指定范围时，从项目规则、架构文档、领域说明、决策记录和主要入口开始，沿真实调用路径逐步调查整个项目，不要求逐文件穷举。

项目较大时可以分阶段汇报。每次说明已经覆盖的范围、尚未深入的区域，以及下一步最值得继续调查的位置。不能因为覆盖有限而声称已经检查完整个项目。

## 判断原则

- 为当前正常需求服务，不为罕见用例、假想扩展或没有现实证据的未来变化增加复杂度。
- 默认相信用户和内部调用者。真实外部边界只做与当前风险相称的简单、集中检查，不为追求完备防御把复杂度扩散到需求无关的位置。
- 兼容性本身没有独立价值。不为未知旧资产、旧调用者或旧环境保留复杂路径；但几行清晰、局部、稳定的兼容代码通常不值得处理。
- 抽象、接口和拆分必须减少调用者需要理解的知识；尽量集中总是一起变化的知识。

重点寻找会影响当前范围整体理解和修改成本的问题，例如分散的规则和状态、泄漏给调用者的编排、紧密耦合的浅层代码、没有现实收益的抽象，以及显著扩大代码路径和测试负担的防御或兼容逻辑。不要把局部命名、格式偏好或单个函数中的普通清理包装成架构问题。

## 排序

按预期净收益排序：综合当前摩擦、影响范围、发生和修改频率、认知负担、缺陷与测试成本，再考虑修复成本、迁移风险和判断不确定性。

不使用机械评分，不要求固定问题数量。没有足够价值的问题时，明确说明当前没有值得修复的架构问题，不为完成报告硬凑候选。

## 汇报

每个候选说明：

- 涉及的代码和真实调用证据；
- 为什么它现在值得修；
- 大致应该集中、删除、简化或保持什么；
- 预期收益、修复成本、主要风险和未知事项。

只提供高层改善方向，不展开具体接口和实施步骤。调查中无法从项目事实确认、又不阻塞其他工作的事项，集中放到报告末尾交给用户裁决，避免频繁打断；只有缺少答案会让整个调查方向可能无效时，才中途询问。
