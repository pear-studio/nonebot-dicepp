# v3.0.0rc17

- 镜像: ghcr.io/pear-studio/nonebot-dicepp:v3.0.0rc17
- Windows: `DicePP-v3.0.0rc17-win64-Portable.zip`、独立 `DicePP-v3.0.0rc17-win64-Setup.exe` 和 `velopack.win-x64.zip`
- 数据变更: no
- 配置变更: yes
- 变更范围: runtime, manager, dashboard, deployment, config, documentation
- 自动升级: no
- 最低 Manager 版本: 1.0

## Added

- Windows 启动器支持无人值守模式（`--background` / `--manager-tray`），后台启动失败会写入 `data/logs/dicepp-runtime.log`。
- Manager API 绑定宿主机回环地址 `127.0.0.1:4091`，同机 Agent 可经 token 鉴权直接调用。

## Changed

- Bot 控制通道从 Dashboard 迁移到 Manager：Bot 经 `DICEPP_MANAGER_URL` 直连 Manager 控制 WebSocket，`DPP_ADMIN_HOST`/`DPP_ADMIN_PORT` 环境变量移除；Manager 统一承载控制通道、心跳与内部 API，Dashboard 不再承载控制 WebSocket。
- Windows 更新契约切换为 contract v2：Release 不再附带独立 nupkg 与 Velopack feed，改为固定命名的 `velopack.win-x64.zip`（内含 manifest 与单个 full nupkg，Manager 校验两层清单、摘要与路径安全后才交给 UpdateGuard）。Release assets 固定为六个：三个平台发行包、`velopack.win-x64.zip`、`dicepp-release.json`、`docker-compose.yml`。
- Linux Compose 拓扑调整：Bot 加入 manager-net 并依赖 Manager 健康后启动；Dashboard 退出 dice-net；`content/` 卷改为可写（仅认证后的 Persona 角色卡路由写入）；新增 Bot 只读挂载的控制凭据目录 `manager/control/`。
- 归档与恢复不再以 Dashboard 启动和健康为前提；未迁移的旧 SQLite 数据库按原样归档与恢复。

## Fixed

- 已配置但 OneBot 客户端未连接的实例，升级/回退的控制心跳健康门必然失败、功能上已成功的回退被误记 rollback_failed；现在按基线时刻有无活跃控制通道判定豁免。
- Windows UpdateGuard 完成程序回滚后，旧版本 Manager 启动恢复与自身维护门冲突，导致事务误记 rollback_failed、Guard marker 残留、后续升级被 409 maintenance_conflict 永久卡死。
- Windows 令牌 ACL 在受信任令牌所有者等场景下的兼容性，失败原因细分。
- Manager 运行时凭据与状态不再进入 Docker 构建上下文。

## Risk Notes

- 所有已部署实例均需手工迁移，不能自动升级到本版本：Linux Compose 的服务/网络/卷/端口与环境变量（移除 `DPP_ADMIN_*`、必须设置 `DICEPP_MANAGER_URL`）均有变化；Windows 旧版本 Manager 只认 contract v1 的 feed 契约，不认识本版本的 bundle 契约。
- Linux 手工迁移使用本版本附带的 docker-compose.yml 重建全部容器，不能只切换镜像 tag。
- 控制凭据目录 `manager/control/` 由 Manager 在迁移后自动生成并分发给 Bot，无需手工操作。
- Manager API 经 `127.0.0.1:4091` 暴露且仅接受 token 鉴权请求；不要把该端口映射到非回环地址。
- 仍在运行 v3.0.0rc11/rc12 的实例升级链路在出厂代码中已损坏，请先按 v3.0.0rc13 Risk Notes 手工迁移。
