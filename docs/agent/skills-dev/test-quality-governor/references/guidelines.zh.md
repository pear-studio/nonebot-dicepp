# 测试质量评分标准与动作策略

## 评分维度

每项 0-2 分，总分 14。

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 失败价值 | 失败时指向真实行为回归 | 失败有一定价值但定位模糊 | 失败多半只是实现变化 |
| 行为契约清晰度 | 明确保护用户行为或模块契约 | 意图可推断但不够清楚 | 只测内部步骤或常量 |
| 断言强度 | 断言关键输出、状态、错误语义 | 断言部分结果或浅层属性 | 只断言不报错、非空、调用次数 |
| 重复风险 | 覆盖独特边界或场景 | 与其他测试部分重叠 | 与其他测试高度重复 |
| mock 风险 | mock 只隔离外部依赖 | mock 掉部分关键协作 | 主要验证 mock 本身 |
| 维护成本 | 小重构不易误伤 | 对实现有一定耦合 | 实现细节变化会大片失败 |
| 层级匹配度 | 单元/集成/e2e 层级合适 | 层级略重或略轻 | 层级明显错误 |

## 质量等级

- `12-14`：高质量，通常 keep。
- `9-11`：可保留，可能需要 rename 或 merge。
- `6-8`：质量一般，通常 rewrite、merge 或 move-layer。
- `3-5`：低质量，通常 delete candidate 或 rewrite。
- `0-2`：噪音测试，通常 delete candidate。

## 硬规则

- 历史回归测试即使分低，也不要自动删除；优先 rewrite 或 rename。
- 核心领域测试即使重复，也先判断是否覆盖不同边界。
- flaky 测试不要直接删除；先判断是否保护重要行为，再考虑 quarantine-flaky 或重写。
- snapshot 测试只有在 snapshot 表达真实契约时才高分；大而不清晰的 snapshot 降分。

## 常见低质量气味

- 测试名无法说明行为，如 `test_case_1`、`test_success`。
- 只断言 `is not None`、长度大于 0、没有异常。
- 只验证 mock 是否被调用，没有验证用户可见行为。
- 测试代码复刻生产逻辑。
- 大量参数只差无意义值，没有覆盖新边界。
- 简单纯函数测试启动完整应用、网络、数据库或机器人框架。
- 复杂协作被 mock 到只剩单个函数调用。

## 常见高质量特征

- 测试名像规格说明。
- 输入、行为、输出或错误语义清楚。
- 失败后能快速说明哪个契约坏了。
- 测试数据覆盖边界、异常和真实使用场景。
- 随机性被 seed、fake 或 property invariant 稳定约束。
- 集成/e2e 数量少但保护关键路径。

## 动作类型

- `keep`：测试有独立行为价值。默认不向用户展示。
- `rename`：测试有价值，但名称无法表达行为。
- `merge`：多个测试覆盖同一规则或同构参数，可合并为参数化或表驱动测试。
- `rewrite`：场景重要，但当前写法低质量。
- `delete`：不保护行为契约，非历史回归，且与其他测试重复或纯噪音。
- `move-layer`：测试层级错误。
- `mark-layer`：marker/tag/分类错误或缺失。
- `quarantine-flaky`：测试不稳定但保护重要行为，先隔离并记录修复建议。
- `add-contract-test`：发现重要行为缺少契约测试，建议补充。

## 自动执行规则

默认执行（low risk + high confidence）：
- 明确重复的测试合并。
- 明显错误或缺失的 marker/tag 修正。
- 行为清楚但命名差的测试重命名。
- 无断言、只断言 mock、且没有历史回归迹象的噪音测试删除。
- 同文件内低风险参数化合并。

谨慎分批执行（medium risk）：
- 涉及 fixture 结构调整。
- 涉及跨文件测试合并。
- 需要更换测试层级。
- 需要把弱断言改成行为断言。

必须询问用户（high risk）：
- 删除核心业务测试。
- 大规模删除或重写。
- 更新大量 snapshot。
- 可能改变项目测试策略。
- 需要修改生产代码。
- 无法判断是否历史回归。

## 删除前检查

- 非核心行为或已有更强测试覆盖。
- 非历史回归或无证据表明是历史回归。
- 断言弱、重复、或只验证实现细节。
- 删除范围小，并能通过相关测试验证。

不要把"不理解"当作删除理由。

## 验证要求

每批改动后运行相关测试。优先最小相关入口；无法确定则运行项目已有 fast/unit 测试入口。

验证失败时：
1. 读取失败输出。
2. 判断是改动错误、测试本身有隐含契约、还是环境问题。
3. 能修正则修正并重跑。
4. 不能修正则回退本批改动并向用户说明原因。
