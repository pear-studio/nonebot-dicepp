# 测试质量评分标准

对测试文件、测试组或单个测试评分。默认优先评估测试组；只有 action item 需要精确到具体测试。

## 维度

每项 0-2 分，总分 14。

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 失败价值 | 失败时指向真实行为回归 | 失败有一定价值但定位模糊 | 失败多半只是实现变化 |
| 行为契约清晰度 | 明确保护用户行为或模块契约 | 意图可推断但不够清楚 | 只测内部步骤或常量 |
| 断言强度 | 断言关键输出、状态、错误语义 | 断言部分结果或浅层属性 | 只断言不报错、非空、调用次数 |
| 重复风险 | 覆盖独特边界或场景 | 与其他测试部分重叠 | 与其他测试高度重复 |
| mock 风险 | mock 只隔离外部依赖 | mock 掉部分关键协作 | 主要验证 mock 本身 |
| 维护成本 | 小重构不易误伤 | 对实现有一定耦合 | 实现细节变化会大片失败 |
| 层级匹配度 | 单元/集成/e2e 层级合适 | 层级略重或略轻 | 层级明显错误 |

## 质量等级

- `12-14`：高质量，通常 keep。
- `9-11`：可保留，可能需要 rename 或 merge。
- `6-8`：质量一般，通常 rewrite、merge 或 move-layer。
- `3-5`：低质量，通常 delete candidate 或 rewrite。
- `0-2`：噪音测试，通常 delete candidate。

## 硬规则

- 历史回归测试即使分低，也不要自动删除；优先 rewrite 或 rename。
- 核心领域测试即使重复，也先判断是否覆盖不同边界。
- flaky 测试不要直接删除；先判断是否保护重要行为，再考虑 quarantine-flaky 或重写。
- snapshot 测试只有在 snapshot 表达真实契约时才高分；大而不清晰的 snapshot 降分。

## 常见低质量气味

- 测试名无法说明行为，如 `test_case_1`、`test_success`。
- 只断言 `is not None`、长度大于 0、没有异常。
- 只验证 mock 是否被调用，没有验证用户可见行为。
- 测试代码复刻生产逻辑。
- 大量参数只差无意义值，没有覆盖新边界。
- 简单纯函数测试启动完整应用、网络、数据库或机器人框架。
- 复杂协作被 mock 到只剩单个函数调用。

## 常见高质量特征

- 测试名像规格说明。
- 输入、行为、输出或错误语义清楚。
- 失败后能快速说明哪个契约坏了。
- 测试数据覆盖边界、异常和真实使用场景。
- 随机性被 seed、fake 或 property invariant 稳定约束。
- 集成/e2e 数量少但保护关键路径。
