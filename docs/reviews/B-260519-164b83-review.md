## R1 [CRITICAL] classify() 关键词不覆盖中文，导致 QuotaExceeded 退化为 UNKNOWN

**位置**: `errors.py:54-82` (_KEYWORD_RULES) + `errors.py:85-111` (classify)
**影响**: `coordinator.py:177` + `session.py:252` + `session.py:288-292`

### 问题描述

`classify()` 的 `_KEYWORD_RULES` 全部使用英文关键词。但实际业务中 `QuotaExceeded` 的 message 来自 `hooks.py:51`:

```python
return PreLLMResult(abort=True, abort_reason="今日配额已用完")
```

"今日配额已用完" 不包含任何英文关键词，`classify(QuotaExceeded("今日配额已用完"))` 返回 `ErrorKind.UNKNOWN`。UNKNOWN 的 `is_retryable=True` (recovery=SWITCH_CANDIDATE)，而旧行为是 `isinstance(e, NON_RETRYABLE_EXCEPTIONS)` → True → immediate abort。

### 影响面

1. **coordinator.py:177**: `if not classify(e).is_retryable` 对 QuotaExceeded 判为 `False`，不会立即将 failures 置为 max，而是 increment by 1，导致 coordinator 在 quota 超限后仍尝试重试，浪费 LLM 调用。

2. **session.py:252**: catch-all 中 `classify(exc)` 对 QuotaExceeded 返回 UNKNOWN, 用户收到 "抱歉，我出错了" 而非配额引导文案。

3. **session.py:289**: `_coordinator_on_exhausted` 中 `user_message(kind, str(last_exception))` 对 QuotaExceeded 也返回通用错误文案。

### 旧行为 vs 新行为对照

| 场景 | 旧行为 (isinstance) | 新行为 (classify) | 正确? |
|------|---------------------|-------------------|-------|
| QuotaExceeded("今日配额已用完") | NON_RETRYABLE, abort | UNKNOWN, retry | **NO** |
| QuotaExceeded("quota exceeded") | NON_RETRYABLE, abort | QUOTA_EXCEEDED, abort | YES |
| NonRetryableError("认证失败") | NON_RETRYABLE, abort | UNKNOWN, retry | **NO** |

### 修复建议

有两种方案（二选一）：

**方案 A**（推荐，改动最小）：在 `classify()` 函数中添加 QuotaExceeded 和 NonRetryableError 的类型检查作为第 1 优先级规则：

```python
def classify(exception: Exception) -> ErrorKind:
    # 0. 已知异常类型直接映射（不依赖关键词）
    if isinstance(exception, QuotaExceeded):
        return ErrorKind.QUOTA_EXCEEDED
    if isinstance(exception, NonRetryableError):
        return _classify_non_retryable(exception)
    # 1. asyncio.TimeoutError 特殊处理
    if isinstance(exception, asyncio.TimeoutError):
        return ErrorKind.NETWORK_ERROR
    # 2. 关键词规则匹配
    ...
```

**方案 B**：在 `_KEYWORD_RULES` 的 QUOTA_EXCEEDED 条目中添加中文字段：

```python
(ErrorKind.QUOTA_EXCEEDED, (
    "quota exceeded", "quota_exceeded", "insufficient_quota",
    "quota limit", "usage limit", "billing", "exceeded your current quota",
    "配额", "已用完",  # 新增中文关键词
)),
```

但中文关键词方案不可靠（不同模块抛出的中文文案格式不一致），推荐 **方案 A**。

## R3 [MEDIUM] `classify_from_provider` 对 `classify_error` 返回 RETRYABLE 时浪费了一次 classify_error 调用

**位置**: `errors.py:114-132`

```python
def classify_from_provider(exception: Exception, provider: object) -> ErrorKind:
    classify_method = getattr(type(provider), 'classify_error', None)
    if classify_method is not None:
        try:
            old_result = classify_method(exception)
            if old_result == ErrorClass.NON_RETRYABLE:
                return _classify_non_retryable(exception)
        except Exception:
            pass
    return classify(exception)
```

当 provider 的 `classify_error` 返回 `ErrorClass.RETRYABLE` 时，函数仍会下落至 `classify()` 做关键词匹配。这意味着在一次错误分类中，关键词匹配逻辑被调用了两次（一次在 provider 的 classify_error 中，一次在 classify 中）。这不是正确性问题，但存在微妙的层级混淆：

- Provider 层的 classify_error 已经基于关键词或状态码判断了 RETRYABLE
- classify() 重新做一遍关键词匹配，可能得出不同于 RETRYABLE 的判断
- 例如：provider 的 classify_error 说 RETRYABLE，但 classify 根据关键词认为是 CONTENT_FILTERED（ABORT）

这产生矛盾的分类结果。Provider 层的 knowledge 被浪费了。

### 建议

当 classify_error 返回 RETRYABLE 时，应继续用 classify() 做细粒度分类吗？如果认为 provider 的 "RETRYABLE 判断" 只是 "不是 NON_RETRYABLE" 的意思，那么当前行为正确。建议补充注释说明这个设计意图。
