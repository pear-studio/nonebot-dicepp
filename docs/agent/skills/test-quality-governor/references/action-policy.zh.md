# 动作策略

## 动作类型

- `keep`：测试有独立行为价值。默认只统计，不逐个输出。
- `rename`：测试有价值，但名称无法表达行为。
- `merge`：多个测试覆盖同一规则或同构参数，可合并为参数化或表驱动测试。
- `rewrite`：场景重要，但当前写法低质量，如弱断言、过度 mock、实现细节耦合。
- `delete`：不保护行为契约，非历史回归，且与其他测试重复或纯噪音。
- `move-layer`：测试层级错误，如纯逻辑用 e2e、复杂协作用过度 mock 单测。
- `mark-layer`：marker/tag/分类错误或缺失。
- `quarantine-flaky`：测试不稳定但保护重要行为，先隔离并记录修复建议。
- `add-contract-test`：发现重要行为缺少契约测试，建议补充。

## 自动执行规则

默认执行：

- `risk=low` 且 `confidence=high`。
- 明确重复的测试合并。
- 明显错误或缺失的 marker/tag 修正。
- 行为清楚但命名差的测试重命名。
- 无断言、只断言 mock、且没有历史回归迹象的噪音测试删除。
- 同文件内低风险参数化合并。

谨慎分批执行：

- `risk=medium`。
- 涉及 fixture 结构调整。
- 涉及跨文件测试合并。
- 需要更换测试层级。
- 需要把弱断言改成行为断言。

必须询问用户：

- `risk=high`。
- 删除核心业务测试。
- 大规模删除或重写。
- 更新大量 snapshot。
- 可能改变项目测试策略。
- 需要修改生产代码。
- 无法判断是否历史回归。

## 验证要求

每批自动改动后运行相关测试。优先选择最小相关入口；如果无法确定，则运行项目已有 fast/unit 测试入口。

验证失败时：

1. 读取失败输出。
2. 判断是改动错误、测试本身有隐含契约、还是环境问题。
3. 能修正则修正并重跑。
4. 不能修正则回退本批改动，记录到 `verification.md`。

## 删除测试前检查

删除前必须满足：

- 非核心行为或已有更强测试覆盖。
- 非历史回归或无证据表明是历史回归。
- 断言弱、重复、或只验证实现细节。
- 删除范围小，并能通过相关测试验证。

不要把“不理解”当作删除理由。
