# backlog-implement — 实施 backlog 条目

从 backlog 中选取一个条目，展示上下文，引导用户完成实现，最终协助清理 backlog。

## 角色

**Implementer Agent** — 负责把 backlog 中的延后项落地为代码改动。

## 参数要求

用户可直接提供 backlog ID，或仅调用技能让 Agent 展示列表供选择：
```
/backlog-implement B-260506-a3f9c1
/backlog-implement              # 无参数，展示列表供选择
```

## 流程

按三个阶段执行：**理解与核实** → **汇报与确认** → **实施**。

> 阶段 B 为强制门禁——未经用户明确确认，禁止进入阶段 C 修改任何代码。

---

### 阶段 A — 理解与核实

1. **获取条目**：
   - 若用户提供了 ID：
     ```bash
     python scripts/tools/backlog.py show <id>
     ```
   - 若无参数：
     ```bash
     python scripts/tools/backlog.py list
     ```
     展示列表，请用户选择一条（回复 ID 或序号）。

2. **核实问题表现**：
   按 `问题表现` 描述去代码里核实——文件 / 函数 / 配置项是否仍然存在？症状是否还可能复现？
   - 若条目已过时（例如对应代码早已被重构掉），向用户说明后改走 `backlog-check` 删除流程，终止本条处理。
   - 核实结果保留，作为阶段 B 汇报的依据。

3. **评估改动意义（满分十分）**：
   基于核实结果，给出改动价值的量化评分。评估维度：
   - 问题真实影响面（曾导致过 bug？调用频率？阻塞后续开发？）
   - 收益率（每增加子系统都需改 vs 一年一两次的低频事件）
   - 风险/收益比（初始化路径重构出新 bug 的代价是否高于维持现状的成本）
   - 方案是否过度工程（低频痛点不应匹配重型架构方案）
   - **评分 ≤5 时，必须向用户建议简化方案或直接跳过**，等待用户决策。

---

### 阶段 B — 汇报与确认（强制门禁）

向用户输出以下三部分，缺一不可：

```
Backlog 条目: [ID] — [标题]

核实结果:
  - <文件/函数是否仍存在，症状是否可复现，当前代码现状>
  - <如有新发现或与条目描述不一致，在此说明>

改动意义评分: X/10 — <一句话理由>

改动方案:
  - 涉及文件: ...
  - 具体改动:
    - ...
  - 不改什么: ...（如有边界需明确）

请确认是否按此方案实施？
```

> **门禁规则**：未收到用户明确确认（如"可以""开始""没问题"等），禁止进入阶段 C。用户提出修改意见时，回到上方更新方案后再次等待确认。

---

### 阶段 C — 实施（用户确认后）

1. **实施**：
   - 按确认的方案改代码。思路以 `工作计划` 字段为起点，但不必照搬——落地时若发现更优方案应优先采用并向用户说明。
   - **简单改动**（单文件、局部逻辑）：直接编辑代码。
   - **复杂改动**（涉及多模块、需设计决策）：建议用户先走 `review0-walkthrough` 或 `opsx:new` 创建独立变更流程，本技能等待其结果。

2. **测试与验证**：
   修改完成后跑项目配套测试（`uv run pytest` 或相关模块测试），确认不破坏现有功能。

3. **清理 backlog**：
   实现并测试通过后，向用户确认是否从 backlog 移除该条目。
   用户确认后：
   ```bash
   python scripts/tools/backlog.py close <id>
   ```

4. **汇报**：
   ```
   Backlog 条目实施完成
   - ID: B-...
   - 标题: ...
   - 改动范围: ...（文件/函数摘要）
   - 已移除 backlog: 是
   ```

## 约束

- **阶段 B 门禁为硬约束**：未经用户明确确认，禁止修改任何代码。核实完毕但用户未确认 → 等待，不得跳过
- 不自动 commit 或 push（受全局规则约束）
- 实现范围以用户确认的改动方案为边界，如需扩大 scope 必须再次经用户同意
- 复杂改动必须走独立设计流程，不得在本技能内直接开搞大重构
- 清理 backlog 前必须完成测试验证
